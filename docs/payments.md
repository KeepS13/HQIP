# 支付 FM 与自动开通

用户在 `https://hqip.sharevps.online/catalog` 新购订阅，每笔新购付款开通一份独立流量包，有效期从实际开通开始计算。已购且未到期的套餐也可在订阅卡片或详情手动续费，保留原订阅并追加一期，详见[套餐续费](subscription-renewals.md)。先在管理端 `/payments` 设置同一支付 FM 商户，再在 `/subscriptions` 设置模板价格。最低 1 元，金额按整数分保存；未定价模板不支持在线购买，管理员仍能直接分配。

## 商户配置

- 接口根地址、商户号、接入密钥：填写 FM 商户后台提供的信息。只接受 HTTPS 公网接口，不关闭证书校验，不跟随重定向。
- 默认通道为 `aloop`，也支持 `alipay`。支付有效期默认 10 分钟，可设置 1–15 分钟。
- 创建和查单使用 POST 表单正文，与旧项目和官方表单/PHP 示例一致；`apiMode=post_form` 指定的是通知发送方式。
- 固定通知地址：`https://api-hqip.sharevps.online/api/v1/payments/fm/notify`。系统下单时自动填写，无需修改旧项目的全局设置。
- 密钥加密保存、不可回显。输入留空表示保持原值；API 明确传入空串才能清除当前密钥。历史版本保留以核验旧订单；关闭支付不停止历史通知和已付款订单的开通。
- 主动查单默认关闭。FM 需要单独开通查单权限，确认拥有权限后再启用。管理员查询限频，用户页面刷新只读取 HQIP 本地数据。

新旧系统即使共用商户，仍使用独立订单号和回调地址。新系统只接收数据库中确实存在的订单，不导入旧项目的订单、套餐续费或资源分配流程。

## 订单与异常处理

管理端 `/orders` 可以查看订单、核验通知时间、开通状态和关联订阅。用户在“我的订单”查看付款倒计时及开通结果。

- 支付链接有效时可继续付款；倒计时结束或用户关闭只停止本地付款入口，不代表支付平台撤单。
- 新购的迟到有效收款通知仍会补开；续费若在订阅到期后才核验付款，保留为“已付款，待人工处理”，管理员重试不能恢复过期订阅。用户或模板停用时也保留待处理。
- 创建请求超时显示“结果待核实”，系统不会盲目重发平台下单请求。先核对订单再明确创建另一单；两笔新购付款分别开通两份，两笔续费付款分别追加一期。
- 没有主动查单权限时，在 FM 商户后台核对并补发通知。不能仅凭截图、浏览器回跳参数或用户声明将订单设为已付款。
- 价格、有效天数、每份节点数量和介绍在下单时保存快照；新购节点在支付期限内预留，续费保留原节点且不预留额外库存，额度等服务限额仍跟随模板。分配、个人库存及迁移规则见[订阅节点分配](subscription-node-allocation.md)。首版不提供退款、余额或零元领取。

## 发布与恢复

SQLite 在启动时事务升级支付表；主业务 schema 仍为 5，支付能力单独标为 `payments_schema_version=1`。已有用户、订阅和流量保留，旧待审批申请转为取消并说明流程已停止。

PostgreSQL 新库初始化包含支付表。已有 PostgreSQL 库需停止控制服务、制作一致性备份，再使用受限的迁移账号环境执行新版本 `hqip migrate-payments`；完成后切回应用账号启动。该命令不改变主密钥和已有订单，重复执行无副作用，应用账号不需要 DDL 权限。SQLite 转 PostgreSQL 前须使用当前版本打开数据库完成升级，再停止服务并制作新快照。

发布清单声明 `paymentsVersion=1`。数据库已有订单或已启用支付时，自动回退拒绝不支持支付的版本。恢复代码和站点配置时保留当前数据库，不用旧快照覆盖新产生的支付与用量。备份必须包含匹配的主密钥；加密商户密钥和支付链接也纳入恢复完整性检查。

此次已授权重新建立空站，旧订单和商户配置只留受限归档，不导入新库，也不继续提供旧域名回调。新站支付默认关闭，管理员重新录入商户配置后使用 `https://api-hqip.sharevps.online/api/v1/payments/fm/notify`。旧站订单若仍需核账，依据归档与支付平台核对，不向新库重放以恢复旧订阅。后续日常发布必须保留新站订单和配置，不能重跑空站初始化。详见[新站部署](fresh-deployment.md)。支付最低金额仍为1元。

真实验收由用户完成小额付款，再验证通知和独立订阅开通；自动化测试仅使用模拟网关，不自动付款。旧设备和 Agent 无需因支付功能升级。
