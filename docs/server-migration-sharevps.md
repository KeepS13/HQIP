# 保留数据迁移控制站

本次迁移来源为 `107.151.244.106`，目标为 `64.83.17.143:22/root`。这是保留现有业务的整站迁移：用户、订阅、订单、余额、用量、租约、服务器、节点、加密凭据与商业配置均需保留。三个正式域名保持不变：`hqip.sharevps.online`、`cms-hqip.sharevps.online`、`api-hqip.sharevps.online`。

本文记录迁移约束和待执行的验收步骤，不是迁移完成回执。仓库中的新部署目标只约束后续 CI；源站是否停止、目标是否接管、DNS 是否切换，必须以实际执行记录和验证结果为准。

## 目标主机与独立运行时

- 目标系统为 Ubuntu 22.04，保留默认 Python 3.10 和已有 PostgreSQL 14，不修改系统 Python 链接、全局 PATH 或其他项目的数据库。
- 在首次运行 HQIP 部署、恢复或备份脚本前，准备与 Ubuntu 22.04 兼容的独立 Python 3.11，入口固定为 `/opt/hqip-runtime/bin/python3`。整个运行时及依赖必须位于 systemd 沙箱可读、root 管理且其他用户不可写的位置，不能依赖 `/root`、临时目录或交互 shell 的环境。
- PostgreSQL 18 客户端工具安装在 `/usr/lib/postgresql/18/bin`，包括 `pg_dump`、`pg_restore` 和 `psql`。HQIP 升级、备份、恢复脚本为子进程单独设置该目录优先的 PATH；不改变 PG14 服务。业务 PostgreSQL 18 与 Redis 8 仍使用 HQIP 独立存储栈和回环端口 15432/16379。
- CI 的远程 Python 命令显式使用独立解释器，安装器的子脚本使用 `sys.executable`；定时备份、失败重试及异常退出记录三个入口也必须使用独立解释器。手动运行控制站 Python 脚本时使用相同的完整路径。
- 先保留源站当前精确 release、清单、`current` 和可用的 previous，完成同版本迁移后才做后续代码发布。不得为迁移改写已有 release 的受校验文件。保留旧版服务期间，操作者须核对实际 unit/必要的 HQIP 专属 drop-in、备份工具选择与运行时；未来安装新完整包会使用仓库中的新 service 文件。

## 迁移与切换顺序

1. 保持 `HQIP_DEPLOY_PAUSED=true`，核对源站活动 SHA、release 哈希、服务、存储和证书清单；为目标配置独立且严格校验的 SSH 主机密钥。迁移执行者负责仓库变量与 secrets，源码变更不会替它们完成切换。
2. 在目标独立准备运行时、HQIP 账号、Nginx 站点、存储与目录权限，核对端口及磁盘余量；只操作 HQIP 专属资源。复制精确发布目录与所需配置，保留 `/var/lib/hqip-control` 中配套 `master.key`、PostgreSQL 标记、必要运行状态，以及 `/etc/hqip-control`、`/etc/hqip-storage` 的私有配置和三个站点的证书/续期配置。秘密文件经受限通道传递，不能进入 Git 或公开日志。
3. 先在独立空数据库演练 PG18 备份恢复并验证应用角色权限、主密钥、schema 和业务数量/摘要，参照[灾备恢复](postgresql-recovery.md)。不能重新生成存储凭据来覆盖迁移配置。恢复工具会设置恢复安全锁；该锁与租约、节点补报必须按实际恢复流程核验。
4. 提前使用同版本 PostgreSQL 物理流复制追平新机，复制仅通过加密隧道访问，并限制复制槽保留的 WAL。最终切换停止旧控制器、后台写入及备份调度，记录最终 WAL 位置与业务表摘要，确认新库完整重放，再停止旧库并提升新库。Redis 在停止旧写入并正常关闭后同步完整持久化文件，保留限流和过期时间；同步配套密钥与最终本地状态。交接须先演练，目标控制面不可用不超过30秒。节点身份、凭据和本地用量账本保留，节点不退役、不重新初始化。
5. 启动新机服务并验证回环两路 `/readyz`，先让旧入口经私有通道转发新服务，再将三个正式域名的现有 A 记录修改为新 IP，保留 Cloudflare 代理和其他属性。核验两个网页、API、客户端、登录会话、订阅、节点续约、用量补报及真实代理连接。切流后观察至少60分钟，旧入口连续15分钟无残余业务请求或活动连接后，才停用旧机 HQIP；其他项目保持运行。
6. 验证服务开机启用配置和独立运行时下的正式备份，在隔离环境恢复该备份，并另存独立受限副本；不通过重启共享主机验证迁移。核对新 SSH 主机密钥和 `DEPLOY_HOST=64.83.17.143`、`DEPLOY_PORT=22`、`DEPLOY_USER=root`，撤销迁移临时权限与旧部署专用授权。仅在迁移验收完成后恢复 CI，后续完整发布使用[自动部署](automatic-deployment.md)。CI 明确拒绝旧 IP。

新库提升前失败可恢复旧服务并取消切换；新库提升后固定使用新库，禁止直接重启旧数据库或以旧快照覆盖新订单、用量及租约。应急控制服务必须连接新库及新 Redis；在无法确认提升状态时不得自动恢复旧写入者。当天撤离以验收通过为条件，准备阶段不足以留出验证时间时不启动切流，不为赶截止强行关闭仍承接用户的入口。

## 与历史空站流程的区别

[全新空站部署](fresh-deployment.md)记录的是历史上明确放弃旧业务、重新建立账户和配置的流程。本次禁止执行 `fresh_deploy.py prepare/activate/finalize`、`init-admin --initialize-postgres`、旧节点退役或空站数据清零步骤。`install_ci_release.py --fresh`只是解包入口，也不能替代整站数据迁移和验收。
